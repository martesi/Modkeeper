## Current Commands Audit

The Modkeeper API is implemented as a set of Tauri commands split into `global` and `library` modules. They utilize `tauri-specta` for TypeScript type generation.

### 1. Library Management (Global & Library)
- `open_library(path)`: Loads an existing library and sets it as active.
- `create_library(requirement)`: Creates a new library and sets it as active.
- `close_library(repo_root)`: Unloads a library from the active state.
- `remove_library(repo_root)`: Deletes a library from disk and unlinks mods.
- `rename_library(name, library_id?)`: Renames a library.
- `rebuild_library_cache(library_id?)`: Forces a re-scan of mod files and updates metadata.

### 2. Mod Operations (Library)
- `get_library()`: Fetches the full state of the active library.
- `add_mods(paths, unknown_mod_name, backup_name)`: Bulk adds mods to the library.
- `remove_mods(ids)`: Bulk removes mods from the library.
- `toggle_mod(id, is_active)`: Enables or disables a single mod.
- `sync_mods()`: Synchronizes the library state with the game directory (deploy/purge).
- `reveal_mod(mod_id)`: Opens the mod folder in the OS file explorer.

### 3. Backup & Documentation (Library)
- `get_backups(mod_id)`: Lists available backups for a mod.
- `create_backup(mod_id, backup_name)`: Creates a new backup.
- `restore_backup(mod_id, timestamp, restore_config)`: Restores a mod from a backup.
- `remove_backup(mod_id, timestamp)`: Deletes a specific backup.
- `get_mod_documentation(mod_id)`: Reads the mod's documentation (e.g., README).

### 4. System & UI (Global)
- `init()`: Called by the frontend on mount to finalize setup and return initial state.
- `apply_window_effect(is_dark?)`: Applies OS-specific window vibrancy (Mica/Acrylic).

---

## Underlying Problems

### 1. High Boilerplate & Ritual
Every command manually clones `Arc` handles (`config_handle`, `instance_handle`) and wraps logic in `tauri::async_runtime::spawn_blocking`. This leads to significant code duplication and makes commands harder to read.
- **Pattern:** `let handle = state.handle.clone(); spawn_blocking(move || { ... })` is repeated ~20 times.

### 2. Inconsistent Return Types
There is no unified response format. Commands return a mix of:
- `LibraryDTO` (The full state)
- `LibrarySwitch` (A subset of state for library switching)
- `()` (Success with no data)
- `Option<String>` (Specific data)

This forces the frontend to handle updates inconsistently, sometimes refreshing the whole store and sometimes doing nothing.

### 3. Fragile Error Handling
The pattern `.map_err(|e| SError::AsyncRuntimeError(e.to_string()))??` is pervasive. It's a symptom of mixing `spawn_blocking` (which returns a `JoinHandle`) with internal `Result` types.

### 4. Lack of Batching Consistency
While `add_mods` and `remove_mods` support bulk operations, `toggle_mod` and `restore_backup` are strictly single-item. This leads to "N-request" problems on the frontend if a user wants to enable 50 mods at once.

### 5. Hidden Context (Active Library)
Most commands implicitly operate on the "active" library stored in `AppRegistry`. While convenient, it makes the API less "REST-like" and harder to debug if the state gets out of sync. Some commands (like `rename_library`) try to bridge this by taking an optional `library_id`, leading to dual-path logic (active vs. specific).

## Optimization Suggestions

### 1. Command Middleware / Wrapper Macro
Implement a procedural macro or a generic wrapper function to handle the `Arc` cloning and `spawn_blocking` ritual.
- **Goal:** Reduce 15 lines of ceremony to 1-2 lines of intent.

### 2. Unified "Response" DTO
Standardize on a `CommandResponse<T>` that can optionally include "Global Updates" (like a refreshed Library list or active library state) alongside the specific requested data. This ensures the frontend always stays in sync with the backend state.

### 3. Batching for All Mod Operations
Refactor `toggle_mod` to `toggle_mods(ids: Vec<String>, is_active: bool)` and similar for other operations. This reduces IPC overhead and allows the backend to perform a single `sync()` after all changes.

### 4. Event-Driven Updates
Instead of returning a massive `LibraryDTO` (which can be megabytes for large libraries) on every small change, use Tauri's `emit` to send granular updates (e.g., `mod-updated`, `sync-progress`) and keep the command return types lean.

### 5. Intent-Based Commands
Instead of `toggle_mod` + `sync_mods`, consider an `apply_changes` command that takes a list of desired states. This moves the complexity of "what needs to happen" to the backend and makes the frontend simpler.

### 6. Resource Pre-loading
The `init()` command currently waits for a background thread. We could optimize this by allowing the frontend to request specific "slices" of data (e.g., just the mod list without all metadata) to speed up initial render.
