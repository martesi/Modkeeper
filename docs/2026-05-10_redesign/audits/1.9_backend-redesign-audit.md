# 1.9 Backend Redesign Audit & Gap Analysis

This audit reviews the current Rust backend (`src-tauri/src/`) of Modkeeper against the **Fidelity Modern** Product Requirements Document (PRD). It outlines the missing database structures, endpoints, sync process changes, and code-style refactoring required to achieve the new design.

---

## 1. Backend API Command Gap Analysis

The PRD defines specific commands for the six core views. Comparing these to the current Tauri command definitions reveals several significant gaps:

| PRD Required Endpoint | Current Closest Endpoint | Status / Gap Details |
| :--- | :--- | :--- |
| `get_profiles()` | `init()` / `get_library()` | **Incomplete:** The current `init()` returns `LibrarySwitch` containing a list of `LibraryDTO`s. We should standardise or introduce `get_profiles()` to return a simplified profile list for the dashboard. |
| `activate_library(profile_id)` | `open_library(path)` | **Gap:** The frontend currently opens libraries by passing their absolute path string. The PRD changes this to identify libraries by a stable `profile_id`. |
| `rebuild_library_cache(profile_id)` | `rebuild_library_cache(library_id?)` | **Incomplete:** Currently uses an optional string to target active or specific libraries. Should be refactored to consistently target by profile ID. |
| `execute_tool(tool_id)` | *None* | **MISSING:** Spawning registered background tools/launchers is completely absent. |
| `save_tool(tool)` | *None* | **MISSING:** CRUD command to save a tool DTO in the library config is completely absent. |
| `delete_tool(tool_id)` | *None* | **MISSING:** CRUD command to delete a tool configuration is completely absent. |
| `toggle_mod_status(mod_id, enabled)` | `toggle_mod(id, is_active)` | **Incomplete:** Currently, toggling a mod only flips `isActive` in memory. The PRD requires immediate disk action (symlink/copy creation or deletion) on toggle. |
| `bulk_update_mods(mod_ids, action)` | `remove_mods(ids)` / `add_mods(paths)` | **MISSING:** We lack a generic bulk-update tool (e.g. enable, disable, delete multiple mods at once) that applies files instantly. |
| `get_installed_mods(query)` | `get_library()` | **MISSING:** The frontend fetches the *entire* library struct to display mods. We should provide a dedicated filtered/sorted query endpoint to support the toolbar's search/filter/sort options efficiently. |

## 2. Technical Gaps & Required Architectures

### A. Executable Tools Subsystem (Complete Feature Gap)
Currently, there is no code, configuration, or data models supporting external tools (like Aki.Server, game launchers, or editors).
1.  **Data Structure (`src-tauri/src/models/library.rs`):**
    We must introduce the `Tool` model inside `LibraryDTO` (and `Library`):
    ```rust
    #[derive(Serialize, Deserialize, specta::Type, Clone, Debug)]
    #[serde(rename_all = "camelCase")]
    pub struct Tool {
        pub id: String,
        pub name: String,
        pub icon: String, // Icon type or custom icon path
        pub executable_path: String,
        pub arguments: String,
    }
    ```
2.  **Tool Storage:**
    Save these configurations inside each library's `manifest.toml` (which represents the `LibraryDTO` on disk). This ensures tools are local to, and switchable with, their active library profile.
3.  **Process Runner:**
    Implement `execute_tool` using Rust's `std::process::Command`. For Windows, ensure child processes are spawned in a background detached state (using Windows-specific command extensions if needed) so that closing Modkeeper does not kill the server process, preventing port binding conflicts on relaunch.

### B. Immediate Sync Pipeline (Flow Redefining)
- **Current Flow:** Toggling a mod in the UI updates the cache struct in-memory and sets `isDirty: true`. The user must manually click the "Sync" button, which calls `sync_mods()` to rebuild the BepInEx/mods directory.
- **Redesigned Flow:** Remove the "Sync" button. Toggles and deletes must be committed immediately on disk:
  - `toggle_mod_status(mod_id, enabled)`: Updates the in-memory cache, then immediately performs link/copy operations for that specific mod folder.
  - `bulk_update_mods(mod_ids, action)`: Operates on multiple mods concurrently, updating their state and applying filesystem changes in a single combined sync step.

## 3. Code-Style & Structural Refactoring (Phase 2 Outline)

To align the backend with the development principles described in `outline-of-redesign.md` and `purpose-of-redesign.md`, the following refactoring must be completed:

### A. OOP vs. FP Boundaries
- **Encapsulated State (OOP):** Maintain `Library`, `GlobalConfig`, and `AppRegistry` as OOP classes. They wrap dirty-flags, path resolution, and state synchronization.
- **Functional Default (FP):** Move all filesystem tasks and mod sorting logic to pure, testable functions that take data structures and return results.
- **Refactoring Targets:**
  - `core/mod_fs.rs`: Strip the `ModFS` struct. Change functions like `resolve_id` and `infer_mod_type` into top-level free functions that operate on paths.
  - `utils/file.rs` and `utils/toml.rs`: Remove empty wrapper structs `FileUtils` and `Toml`. Expose pure, free functions (e.g. `pub fn copy_recursive`, `pub fn read_toml`).

### B. Clean Core/Service/Interface Separation
1.  **Interface Layer (`commands/`)**:
    - Strip all boilerplate. Currently, every command clones `Arc` handles and wraps work in `tauri::async_runtime::spawn_blocking`.
    - **Refactor:** Build a middleware macro or a helper closure to handle `Arc` extraction and blocking thread scheduling, reducing command boilerplate from ~15 lines to 2 lines.
2.  **Service Layer (`core/*_service.rs`)**:
    - Expose logical orchestration endpoints that connect the interface layer to core operations. Services must not handle Tauri-specific types.
3.  **Removal of Comments**:
    - As requested, strip all comments from the backend source code. Code must be structured cleanly so that it is self-explanatory.

## 4. Summary of Verification Plan

1.  **Automated Unit Tests:**
    - Rewrite `tests/library.rs` and `tests/mod_fs.rs` to reflect the hash-only structure (no manifest references).
    - Add tests for tool registration configurations and path validations.
2.  **Windows Verification:**
    - Ensure background tools launched via `execute_tool` run independently and do not hang when Modkeeper is terminated.
    - Validate that directory linking defaults to symlinks and correctly falls back to file-copying operations.
