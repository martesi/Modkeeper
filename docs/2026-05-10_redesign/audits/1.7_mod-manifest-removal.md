# 1.7 Audit: Mod Manifest Removal & Hash-Only Behavior

This audit analyzes the impact and benefits of removing support for individual mod manifests (`manifest/manifest.json`) and transitioning exclusively to content-based folder hashing for mod identification and naming.

---

## 1. Summary of Proposed Changes

Currently, Modkeeper uses a two-tier mod identification strategy:
1. **Priority 1 (Manifest):** Reads a custom `manifest/manifest.json` file inside the mod folder to determine the mod's ID, name, version, compatibility rules, links, and dependencies.
2. **Priority 2 (Hashing):** Fallback mechanism that builds a stable, deterministic ID based on the file layout (DLL paths under client plugins and folder names under server mods).

By **removing support for the mod manifest**, we transition to a **hash-only model**.
- **Mod ID:** Generated strictly using the existing hashing logic.
- **Mod Name:** Determined by the directory name (loose files/directories) or the ZIP file name (archives).
- **Mod Metadata:** Version, author, description, and documentation are entirely removed.
- **Dependency & Compatibility Checking:** Dropped entirely from the application core.

## 3. Impact on Tests

Several unit and integration tests set up mock directories containing `manifest/manifest.json` files. These will need to be refactored:
- **`src-tauri/tests/library.rs`:** Several integration tests (such as `test_add_mods`, `test_rebuild_cache`, and `test_get_library`) mock manifest files to force specific mod names and IDs. These should be refactored to verify that folder hashing generates correct, consistent IDs and uses folder/zip names.
- **`src-tauri/tests/mod_fs.rs`:** The test `test_collect_files_excludes_manifest` should be removed since we no longer have a special `manifest` directory that must be filtered out of the mod file list.

## 4. Architectural & UI Redesign Benefits

Removing support for the mod manifest directly benefits the **new UI redesign** (`docs/2026-05-10_redesign`) in several key ways:

### 1. Radically Simplified Mod Details View
The mod details view currently attempts to display a full page of metadata, links, compatibility lists, dependency graphs, and a README markdown renderer. 
- **Without Manifests:** The mod view becomes lightweight. It only needs to show the Mod Name, ID, Type (Client/Server/Both), and the backup history list.
- **Outcome:** Reduces the UI design surface for the detail page by roughly **70%**, enabling a cleaner, more cohesive design.

### 2. Zero Dependency-Resolution Headaches
Managing local dependency checks introduces complex visual states (e.g. missing dependencies, version mismatches, optional vs. required flags).
- **Without Manifests:** We no longer need warnings, tooltips, or alert states for broken dependencies on the library dashboard or mod list.
- **Outcome:** The mod list renders instantly without running SemVer checks, and UI layouts remain clean and uncluttered.

### 3. NPM Dependency & Bundle Size Reduction
Rendering markdown and checking semver requires heavy dependencies.
- **Without Manifests:** We can uninstall `react-markdown`, `remark-gfm`, and `semver`.
- **Outcome:** Smaller client-side bundle size, faster Vite dev start times, and fewer dependencies to maintain.

### 4. Cleaner Tauri API and Type Bindings
- The Tauri commands don't need custom DTO mapping (`dto_builder.rs` is removed) because the library serialization matches what is stored in the cache exactly.
- Type bindings generated in `bindings.ts` shrink by ~100 lines, eliminating dead interfaces like `ModManifest`, `Link`, etc.
