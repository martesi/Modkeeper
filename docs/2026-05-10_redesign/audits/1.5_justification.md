## What Are The Drawbacks if using FP in `library.rs` etc. ?

While the redesign prioritizes FP, forcing it onto core state managers like `Library` or `AppRegistry` has several drawbacks:

1.  **Parameter Threading (Prop Drilling):** Functions that perform library operations (e.g., `add_mod`, `sync`) would need to accept many individual parameters (repo root, game root, spt rules, cache, etc.) instead of a single `&Library` reference.
2.  **Ownership Complexity:** Rust's ownership model makes "pure" FP (where state is always returned and replaced) more expensive due to potential cloning. OOP allows safe, in-place mutation via `&mut self`.
3.  **Loss of Encapsulation:** `Library` currently manages its own "dirty" state (`is_dirty`). In a pure FP model, the caller would have to track whether the returned state changed and whether it needs to be persisted to disk.
4.  **Boilerplate:** Converting every method to a free function often leads to a "Service" layer that just passes data around, which can feel redundant for simple state-heavy tasks.

**Verdict:** Keep `Library` and `Registry` as OOP state containers (the "Managers"), but ensure the logic inside their methods is composed of pure FP functions from core/util modules.
